**Что сделано:** Разбор жалобы «автодополнение не работает, товары
пропадают, переходы долгие» — два разных источника, один баг починен.

**Источник 1 — реальная латентность БД разработки, не баг.** `.env`
указывает на боевой shared-хостинг (`mikhail700.beget.tech`) — каждый
запрос к БД из дев-окружения идёт по интернету. Замерено напрямую:
подключение ~2 с (один раз на запрос), простой `SELECT` — 250–800 мс.
`ProductController::show()` делает 6 последовательных Model-вызовов
(товар, фото, варианты, атрибуты, похожие, инкремент просмотров) —
итого ~2.2 с только на сетевые round-trip'ы, без какой-либо лишней
работы в PHP. Это объясняет «долго открывается карточка товара» и
«долго думает перед переходом по страницам» (пагинация тоже — 2
последовательных запроса на `/search`/`/catalog/{slug}`). Не правка
для Таска 6 — общее свойство инфраструктуры, одинаково будет на любой
странице сайта; на проде фронт и БД физически рядом, задержка другая.

**Источник 2 — реальный баг в `public/assets/js/search.js`.**
`fetchSuggestions()` не имела защиты от гонки запросов: пока
пользователь печатает, уходит по fetch на каждый символ (после
debounce), и при нестабильной задержке ответ на **более ранний**
(уже неактуальный) запрос мог прийти **позже** ответа на актуальный —
`renderSuggestions()` неусловно перезаписывал уже показанный
корректный список устаревшим/пустым. Со стороны это выглядело как
«найденные товары пропадают». Высокая латентность БД выше не создала
этот баг, а лишь сделала гонку практически гарантированной вместо
редкой.

Исправлено: `AbortController` — каждый новый вызов `fetchSuggestions()`
обрывает предыдущий ещё не завершившийся запрос; в `catch` `AbortError`
игнорируется (это ожидаемая отмена, не сбой). Отмена дополнительно
вызывается при полной очистке поля ввода, чтобы поздний ответ не
показал подсказки поверх уже пустого поля.
