## Решения таска

**`Core/catalog.php` остаётся без обращений к БД.** `parseFilters()`
валидирует и клампит значения из `$_GET` чисто на уровне типов и границ
(числа, диапазоны, известные бакеты); проверка существования
`vendor_id` не нужна — bound-параметр в `IN (?, ?, …)` безопасен и для
несуществующего id, просто не даст совпадений.

**Рейтинг — «от N звёзд», не точное совпадение.** Несколько отмеченных
чекбоксов сводятся к одному условию `rating_avg >= MIN(выбранные)` —
это эквивалентно OR из условий «больше-равно» и проще на SQL.

**Наличие.** «Только в наличии» — это `stock_quantity > 0` для простых
товаров (`has_variants = 0`) ИЛИ существование хотя бы одного варианта
с `stock_quantity > 0` для `has_variants = 1` (`EXISTS` по
`product_variants`).

**Переключатель вида — cookie, не сессия.** `?view=` в URL для конкретной
ссылки важнее cookie; если параметра в URL нет — берётся cookie; если
нет ни того, ни другого — `grid`. Первая версия делала кнопки
`grid-btn`/`list-btn` обычными ссылками `?view=grid`/`?view=list` —
работало и без JS, но давало заметную перезагрузку страницы поверх уже
мгновенного визуального переключения (его и так делает вендорный
`script.js` темы по клику на `.grid-btn`/`.list-btn`). По просьбе
пользователя после первой проверки переделано: кнопки — `javascript:void(0)`
с `data-view-link`, `catalog.js` по клику лишь пишет cookie `view`
(`document.cookie`) без навигации. Прямые ссылки `?view=list`/`?view=grid`
(например, из письма или закладки) по-прежнему работают — их читает
`CatalogController::resolveAndPersistView()` и ставит ту же cookie.

**Пагинация и фильтры дружат уже сейчас.** `buildQuery()` (Таск 3)
сохраняет весь текущий `$_GET`, значит переход по страницам и смена
сортировки автоматически сохраняют выбранные фильтры без доп. правок.

**Найдено при реализации: `render()` уже занял имя `$view`.** У
`render(string $view, array $data)` (Core/functions.php) параметр
шаблона называется `$view` — если передать в `$data` ключ `'view'`,
`extract($data, EXTR_SKIP)` молча его отбрасывает (переменная с этим
именем уже существует), и в шаблоне `$view` останется путём к файлу, а
не `grid`/`list`. Внешне не падает ошибкой — переключатель просто всегда
выглядел бы как «плитка». Ключ и переменная в контроллере/вью
переименованы в `viewMode`; `render()` не трогали — это общая функция
вне scope таска.

**Найдено при реализации: офканвас-механика темы для сайдбара нигде не
была подключена.** `.left-box` на мобильном — `position:fixed; left:-350px`
по умолчанию (см. `style.css`), появляется только через `.show`,
которую переключает `filter-sidebar.js` по клику на `.filter-button`.
Ни в Таске 2, ни в Таске 3 этот файл не копировался и кнопка не
добавлялась — раньше в сайдбаре было только дерево категорий, схлопывать
было особо нечего. С появлением блока фильтров в этом таске без него на
320px сайдбар был бы просто невидим. Добавлены: `filter-sidebar.js`
(vendor, as is), кнопка «Фильтры» (`.filter-button`) в `.show-button`
контентной колонки, `.back-button` и единый `.left-box`, оборачивающий
теперь и дерево категорий, и блок фильтров (было два разных `.left-box`
— объединены в один, как в оригинальной вёрстке), `.bg-overlay` в конце
страницы.
